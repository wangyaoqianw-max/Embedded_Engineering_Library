# Embedded Firmware Architecture

## 1. 架构说明

本工程采用分层式固件架构，主要用于 STM32 等嵌入式项目开发。

核心分层关系：

```text
APP
 ↓
Service
 ↓
Platform
 ↓
Impl
 ↓
Vendors / HAL / Hardware
```

设计目标是降低业务逻辑与具体硬件实现之间的耦合，使模块职责更加清晰，并提高代码的可维护性、可测试性和可移植性。

------

## 2. 目录结构

```text
Project/
├── 00_Config/          # 工程配置
├── 00_Doc/             # 固件设计与开发文档
│
├── 01_APP/             # 应用层
├── 02_Service/         # 服务层
├── 03_Platform/        # 平台抽象层
├── 04_Impl/            # 平台具体实现
├── 05_Vendors/         # 第三方组件
│
├── Core/               # CubeMX 生成的核心代码
├── Drivers/            # STM32 HAL/LL、CMSIS 等驱动
├── Middlewares/        # FreeRTOS 等中间件
├── MDK-ARM/            # Keil 工程文件
└── *.ioc               # STM32CubeMX 配置文件
```

------

## 3. 各层职责

### 01_APP

应用层负责产品业务逻辑和系统运行流程，例如：

- 系统状态管理
- 应用任务组织
- 业务状态机
- Service 模块调用
- 产品功能流程

APP 层原则上不直接调用 STM32 HAL API。

------

### 02_Service

Service 层提供相对独立的软件功能和业务服务，例如：

- Ring Buffer
- UART 数据接收服务
- 通信协议解析
- Log 服务
- Storage 服务
- Sensor 服务
- Firmware Update / OTA 服务
- 数据处理模块

Service 可以依赖 Platform 提供的硬件能力，但应尽量避免依赖具体 MCU。

------

### 03_Platform

Platform 层定义上层需要使用的硬件或系统能力，对具体实现进行抽象。

例如：

```c
platform_uart_send();
platform_flash_read();
platform_flash_write();
platform_get_tick();
```

上层模块只依赖 Platform 接口，不直接依赖 HAL、FreeRTOS 或具体外设实例。

------

### 04_Impl

Impl 层负责 Platform 接口的具体实现，例如：

```text
platform_uart_send()
        ↓
stm32_uart_impl.c
        ↓
HAL_UART_Transmit_DMA()
```

Impl 层通常与以下内容直接相关：

- STM32 HAL / LL
- MCU 外设
- DMA
- Interrupt
- FreeRTOS
- BSP
- 具体硬件资源

更换 MCU、外设实例或底层驱动时，应优先限制修改范围在 Impl 层。

------

### 05_Vendors

存放第三方软件组件或移植后的外部库，例如：

- EasyLogger
- 第三方协议库
- 文件系统
- 算法库
- 第三方驱动组件

原则上尽量减少直接修改第三方源码，必要的适配代码优先放在 Platform / Impl 层。

------

### 00_Config

保存项目级软件配置，例如：

- 功能开关
- Buffer Size
- Task 参数
- 超时时间
- 模块配置
- 编译配置

避免将大量 Magic Number 分散在各模块内部。

------

### 00_Doc

保存与固件开发直接相关的工程文档，例如：

```text
Requirements
Solution Design
Firmware Architecture
Interface Design
Task / Interrupt Design
Communication Protocol
Memory Map
Test Plan
Debug Record
Decision Log
```

文档根据项目复杂度按需创建，不要求所有项目具备完整文档集合。

------

## 4. CubeMX 生成代码

以下目录通常由 STM32CubeMX/ST 工具生成或维护：

```text
Core/
Drivers/
Middlewares/
```

业务逻辑原则上不直接堆积在：

```text
main.c
stm32xxxx_it.c
usart.c
spi.c
gpio.c
```

这些文件主要负责：

- 外设初始化
- HAL 回调入口
- 中断入口
- 与自定义架构之间的适配

复杂逻辑应转移到 APP、Service、Platform 或 Impl 中。

必须修改 CubeMX 生成文件时，应尽量放在：

```c
/* USER CODE BEGIN */

/* USER CODE END */
```

保护区域内。

------

## 5. 依赖原则

推荐依赖方向：

```text
APP
 │
 ▼
Service
 │
 ▼
Platform
 │
 ▼
Impl
 │
 ▼
HAL / RTOS / Hardware
```

基本原则：

- 上层可以依赖下层抽象。
- 下层不应依赖具体业务逻辑。
- Service 不应直接绑定具体 STM32 外设。
- Platform 负责定义能力，Impl 负责实现能力。
- 第三方组件与业务代码之间尽量通过适配层隔离。
- 避免跨层直接调用导致架构失效。

------

## 6. 模块放置示例

以 `UART + DMA + RingBuffer` 为例：

```text
01_APP/
└── communication_app.c

02_Service/
├── uart_service.c
└── ring_buffer.c

03_Platform/
└── platform_uart.h

04_Impl/
└── stm32_uart_impl.c

Core/
└── Src/usart.c
```

数据链路可以表示为：

```text
UART Hardware
     ↓
DMA / HAL
     ↓
Impl
     ↓
Platform
     ↓
Service
     ↓
APP
```

## 7. 开发原则

新增功能时推荐按照以下顺序推进：

```text
需求
→ 技术方案
→ 模块划分
→ 接口设计
→ Task拆分
→ 分阶段实现
→ 模块测试
→ 联调
→ Debug
→ Code Review
→ 重构与文档更新
```

新增模块前应优先确认：

1. 模块属于哪一层。
2. 模块负责什么。
3. 模块不负责什么。
4. 对上提供哪些接口。
5. 向下依赖哪些能力。
6. 是否存在中断、DMA、RTOS或共享资源问题。
7. 如何独立验证模块正确性。

工程架构服务于项目，不强制所有功能进行复杂分层。对于简单模块允许适当裁剪，但应避免长期累积跨层调用和业务逻辑与硬件实现耦合。
